# nGrinder 부하테스트 요약

## 목적

서비스 부하 증가 시 응답 지연의 원인을 서버 전체 자원 부족으로 단정하지 않고, 관측 지표와 요청별 응답시간을 근거로 병목 범위를 좁힌 뒤 동일 조건에서 개선 효과를 검증했습니다.

## 테스트 환경

| 구분 | 내용 |
| --- | --- |
| 대상 | Docker Compose 기반 밀플래닝 서비스 11개 |
| 부하 도구 | nGrinder `3.5.9-p1` |
| 관측 | Grafana · Prometheus · Loki · Tempo |
| 확인 지표 | VUser · TPS · 평균 응답시간 · 오류율 · VM CPU · 요청별 지연 |

## 1. 혼합 요청 부하로 병목 범위 확인

| VUser | 요청 수 | 오류율 | 평균 응답시간 | TPS | VM 최대 CPU |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 36,081 | 0% | 96.66ms | 321.68 | 17.73% |
| 200 | 37,932 | 0% | 348.63ms | 338.32 | 18.11% |
| 300 | 38,116 | 0.0105% | 593.80ms | 342.97 | 18.39% |

- 200→300 VUser에서 부하는 50% 증가했지만 TPS는 약 1.4%만 증가했고, 평균 응답시간은 약 70% 증가했습니다.
- VM CPU는 약 18%로 여유가 있어, 서버 전체 증설보다 요청 경로별 지연을 우선 분석했습니다.
- Price 현재가·핫딜 요청에서 최대 약 8.6초 지연을 확인해 Price API를 우선 점검 대상으로 좁혔습니다.

## 2. 동일 조건 재검증

팀의 공통 가격 View 물질화와 Redis 읽기 캐시 적용 후, 같은 200 VUser 조건으로 Price API를 재검증했습니다.

| 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| TPS | 58.2 | 94.98 |
| 평균 응답시간 | 1,407ms | 4.48ms |
| 오류 | 0건 | 0건 |
| P95 / P99 | - | 2ms / 6ms |

## 결과

- Price API 평균 응답시간 **1,407ms → 4.48ms**, 약 **99.7% 감소**
- 단순 서버 증설 대신 관측 지표와 요청별 지연을 근거로 병목 범위를 좁히고, 동일 조건으로 개선 효과를 재검증
